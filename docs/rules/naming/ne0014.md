# NE0014: Avoid non-representable characters

| Property   | Value   |
|------------|---------|
| Rule ID    | NE0014  |
| Category   | Naming  |
| Severity   | Warning |
| Code fix   | Yes     |

## Cause

A Unicode character from the "Format" general category (`Cf`) — for example a zero-width space/joiner
(`U+200B`, `U+200D`), a byte-order mark (`U+FEFF`), or a bidirectional text-direction override
(`U+202A`–`U+202E`, `U+2066`–`U+2069`) — appears either inside a declared identifier, or as stray
whitespace immediately before a token.

## Rule description

The C# language specification allows a "formatting character" (Unicode category `Cf`) anywhere inside an
identifier, so a name containing one compiles without error or warning from the compiler itself. These
characters typically render as invisible, or render inconsistently across editors, terminals, and diff
tools — a pasted or copied identifier can carry one along without anyone noticing. Two declarations that
look identical in an editor can be different symbols entirely if one of them hides such a character, and a
review of a diff can miss the character being added or removed altogether.

The rule inspects two distinct places:

1. **Declared identifiers.** The name of:
   - Types (classes, structs, interfaces, records, enums, delegates) and type parameters.
   - Methods, local functions, properties, events, enum members, and fields/local variables (each variable
     declarator).
   - Parameters, catch-block exception variables, and pattern variables (`is` patterns, `out` variables,
     `foreach` iteration variables).
   - Every segment of a namespace declaration's name (e.g. both `My` and `Project` in `namespace
     My.Project;`).

   Only the declaration is reported — not every place the identifier is subsequently referenced — because
   fixing the declaration's name (see below) resolves every reference at once.

2. **Stray whitespace before a token** — in practice this only ever fires for a byte-order mark
   (`U+FEFF`) that arrives as literal text content, for example one pasted right before a `namespace`
   declaration. The C# lexer specifically treats a *literal* byte-order mark as whitespace wherever it
   sits; every other "Format" character in that same free-standing position instead causes a hard compiler
   error (`CS1056`), so only a literal byte-order mark risks being silently swallowed this way.

Generated code is skipped. Comments, string literals, and character literals are left alone — free-form
text may legitimately contain these characters.

### Known limitations

- Tuple element names and anonymous type member names are not currently inspected.
- A namespace segment is fixed only at the specific declaration flagged — see below.
- **A genuine file-level encoding BOM is not, and cannot be, detected by this rule.** The three-byte
  `EF BB BF` sequence a text editor writes at the very start of a UTF-8 file is consumed by Roslyn's own
  encoding detection before the compiler ever tokenizes the file — it never becomes text, so no analyzer can
  see it. Case 2 above only catches a byte-order-mark *character* that ends up as literal content partway
  through a file (e.g. from a bad copy-paste or a file concatenation), which is a different, much rarer
  situation. If a `.cs` file itself was saved with a UTF-8 BOM and that is undesired, that is an editor,
  `.editorconfig`, or `.gitattributes` (`* text=auto` / `working-tree-encoding`) concern, not something a
  Roslyn analyzer can flag or fix.

## How to fix violations

Remove the offending character(s):

```csharp
// Before — the class name contains a zero-width space (U+200B) between "My" and "Class"
public sealed class My​Class
{
}

// After
public sealed class MyClass
{
}
```

The code fix applied depends on which of the two cases was flagged:

- **A type, member, parameter, type parameter, or local variable identifier** is renamed to the same name
  with every "Format" character stripped out, using Roslyn's symbol renamer so every reference across the
  solution is updated together with the declaration. If stripping the characters would leave nothing
  behind, no fix is offered — the diagnostic still reports so the declaration can be renamed by hand.
- **A namespace segment, or stray whitespace before a token** (the byte-order-mark case) is fixed with a
  plain text edit local to that occurrence, not a solution-wide rename. A namespace is not renamed through
  Roslyn's symbol renamer here: asking the semantic model for the declared symbol of a multi-segment
  `namespace A.B;` resolves to the innermost merged namespace (`A.B`), not the specific outer segment (`A`)
  that was flagged, so renaming that symbol would rename the wrong segment. If another file references the
  same namespace segment (e.g. via a `using` directive) with the same characters still in place, re-run the
  fix there too.

## Suppress a warning

```csharp
#pragma warning disable NE0014
#pragma warning restore NE0014
```
