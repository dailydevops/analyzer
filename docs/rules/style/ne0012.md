# NE0012: Use an explicit numeric literal suffix

| Property   | Value   |
|------------|---------|
| Rule ID    | NE0012  |
| Category   | Style   |
| Severity   | Info    |
| Code fix   | Yes     |

## Cause

A numeric literal is converted to `long`, `ulong`, `uint`, `float`, `double`, or `decimal` without carrying
that type's canonical, upper-case suffix.

## Rule description

Each of the six types above has a dedicated literal suffix — `L`, `UL`, `U`, `F`, `D`, `M` — that states the
literal's type explicitly instead of relying on an implicit conversion from the compiler's default type for
an unsuffixed literal (`int` for a whole number, `double` for one with a decimal point or exponent).

The rule inspects every numeric literal against the type it's converted to, in any context — assignment,
comparison, argument, return, and so on — not only a fixed set of syntactic shapes. A literal that already
carries the correct suffix, in any case, is left alone; one with the wrong suffix, or none at all, is
flagged.

A hexadecimal (`0x...`) or binary (`0b...`) integer literal converted to `float`, `double`, or `decimal` is
left alone — that format has no floating-point or decimal suffix to add.

Generated code is skipped.

## How to fix violations

Add or correct the literal's suffix:

```csharp
// Before
long a = 0;
double b = 1.5;
decimal c = 10;

// After
long a = 0L;
double b = 1.5D;
decimal c = 10M;
```

The code fix performs this rewrite for a single occurrence, and via Fix All for every occurrence in the
selected scope.

## Suppress a warning

```csharp
#pragma warning disable NE0012
#pragma warning restore NE0012
```

## Interaction with SonarAnalyzer.CSharp's S818

If [SonarAnalyzer.CSharp](https://github.com/SonarSource/sonar-dotnet) is also active, its `S818` ("Literal
suffixes should be upper case") can flag the same literal when it has a suffix with the wrong letter written
in lower case (for example `0u` where a `long` is expected — wrong letter *and* wrong case). A
`DiagnosticSuppressor` bundled with this package (`NES0002`) suppresses `S818` wherever NE0012 already
reports the same literal, so both analyzers don't offer two conflicting fixes. `S818` still fires on its own
when only the case is wrong (for example `0l` where `long` is expected), since NE0012 normalizes case before
comparing and doesn't flag that.
