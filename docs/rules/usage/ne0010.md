# NE0010: Accept a CancellationToken parameter on an asynchronous method

| Property   | Value   |
|------------|---------|
| Rule ID    | NE0010  |
| Category   | Usage   |
| Severity   | Warning |
| Code fix   | Yes     |

## Cause

A method's return type is `System.Threading.Tasks.Task`, `Task<T>`, `System.Threading.Tasks.ValueTask`,
`ValueTask<T>`, or `System.Collections.Generic.IAsyncEnumerable<T>`, and the method declares no parameter of
type `System.Threading.CancellationToken`.

## Rule description

A method returning one of these types represents an asynchronous operation a caller may want to cancel.
Accepting a `CancellationToken` parameter lets the caller request cancellation and lets the method propagate
that token to whatever it awaits or yields from. A method that omits the parameter entirely cannot honor a
cancellation request at all.

The following are not flagged, because their signature is constrained by a contract elsewhere rather than
freely chosen:

- A method marked `override` — the signature is fixed by the member it overrides.
- An explicit interface implementation (`Task ISample.Run()`) — the signature is fixed by the interface.
- A method that implicitly implements an interface member — the signature is fixed by the interface it
  implements.
- Local functions, lambdas, and anonymous methods are never considered — only methods declared directly on a
  type or interface are.
- A partial method is reported only once, on the implementing declaration, not on the defining declaration.

An interface's own method declaration is still flagged when it is missing the parameter, since it is the
contract that constrains everything above; only the implementing/overriding side is excluded.

A method that has a body (a block or expression body) is only flagged when that body has some actual use for
the parameter: a call site the token could be passed to (either an unfilled trailing `CancellationToken`
parameter, or exactly one sibling overload that adds one), or an expression that produces or consumes a
`CancellationToken` without already being wired straight into a call as an argument. A hardcoded
`CancellationToken.None` is the exception: since it signals "no cancellation" rather than a real token, it
still counts as evidence the method needs its own parameter, even when passed straight into a call. Otherwise,
the parameter the code fix would add could never be used, and the only visible effect would be an
unused-parameter warning from another analyzer. A method without a body — abstract, interface, or extern — has
no such body to leave with an unused parameter, so it is always flagged regardless.

```csharp
// Not flagged: nothing in the body could use a token.
public Task GetStatusAsync() => Task.FromResult(Status.Ready);

// Flagged: the token could be passed through to FindAsync.
public Task<Order> GetOrderAsync(int id) => _repository.FindAsync(id);

// Not flagged: the call already gets a genuine token, just from an ambient source, not this method's own
// parameter.
public Task RunAsync() => _repository.FindAsync(SomeContext.Current.CancellationToken);
```

Generated code is skipped.

## How to fix violations

Add a `CancellationToken` parameter, typically last and with a default value so existing call sites keep
compiling:

```csharp
// Before
public Task<Order> GetOrderAsync(int id) => _repository.FindAsync(id);

// After
public Task<Order> GetOrderAsync(int id, CancellationToken cancellationToken = default) =>
    _repository.FindAsync(id, cancellationToken: cancellationToken);
```

The code fix appends `CancellationToken cancellationToken = default` as the method's last parameter and adds
a `using System.Threading;` directive if the file does not already have one in scope.

On a best-effort basis, it also passes the new token through to call sites within the method's own
body/expression-body — but only where doing so is unambiguous and doesn't change which method overload a
caller ends up invoking. The token is always appended as a named argument
(`cancellationToken: cancellationToken`), not positionally, so it can reach its target parameter even when
other optional parameters follow it:

- The call already targets a method with an unfilled `CancellationToken` parameter (typically an optional
  one, as in the example above) at or past the arguments already supplied — the token fills that slot by
  name, whether or not it's the method's last parameter, as long as every other parameter following the
  supplied arguments also has a default value.
- The call targets a method with no `CancellationToken` parameter at all, but there is exactly one sibling
  overload with the same parameters plus one added `CancellationToken` — the token is appended by name so
  overload resolution picks that overload instead, again as long as every other newly-introduced parameter
  has a default value.

Calls that already pass a `CancellationToken` explicitly, that already use named/`ref`/`out` arguments, or
that sit inside a nested lambda, anonymous method, or local function, are left untouched — the fix does not
guess whether an already-cancellation-aware call site or a nested closure's own token handling should change.

## Suppress a warning

```csharp
#pragma warning disable NE0010
#pragma warning restore NE0010
```
