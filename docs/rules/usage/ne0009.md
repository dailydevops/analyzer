# NE0009: Check for cancellation at the start of the method or local function body

| Property   | Value   |
|------------|---------|
| Rule ID    | NE0009  |
| Category   | Usage   |
| Severity   | Warning |
| Code fix   | Yes     |

## Cause

A method or local function with a block body accepts a `System.Threading.CancellationToken` parameter but does
not check for cancellation as the first statement of its body.

## Rule description

A method or local function that accepts a `CancellationToken` should honor it as early as possible, before
doing any other work. The check must appear as the first statement of the body, immediately after any leading
argument-validation guard clauses. Either of the following satisfies the rule:

```csharp
cancellationToken.ThrowIfCancellationRequested();
```

```csharp
if (cancellationToken.IsCancellationRequested)
{
    return;
}
```

Leading guard clauses are skipped over when locating "the start" of the body:

- An `if` statement whose sole statement throws an exception that is or derives from `System.Exception` — this
  covers argument-validation guards (`ArgumentException`, `ArgumentNullException`,
  `ArgumentOutOfRangeException`, and custom subclasses) as well as state-validation guards
  (`InvalidOperationException` and any other exception type), for example
  `if (value is null) throw new ArgumentNullException(nameof(value));` or
  `if (_context is null) throw new InvalidOperationException();`. Either way the guard only ever throws or
  falls through, so it does no "other work" the rule cares about ordering the cancellation check against.
- A call to a static `ThrowIfXxx` guard-helper method on a type whose name ends with `Exception`, for example
  `ArgumentNullException.ThrowIfNull(value)` or `ArgumentException.ThrowIfNullOrEmpty(text)`.

The very next statement after the last guard clause (or the very first statement, if there are no guard
clauses) must be the cancellation check. If a method declares more than one `CancellationToken` parameter,
checking against any one of them satisfies the rule.

If that statement is instead a `for`, `foreach`, `while`, or `do` loop, the check may sit as the first
statement of the loop's body — guarding the loop's own work satisfies the rule just as well as guarding the
method's:

```csharp
public void Run(IEnumerable<Item> items, CancellationToken cancellationToken)
{
    foreach (var item in items)
    {
        cancellationToken.ThrowIfCancellationRequested();

        Process(item);
    }
}
```

This applies at any nesting depth — a loop nested inside another loop is matched as long as its own leading
statement is the check:

```csharp
public void Run(int rows, int columns, CancellationToken cancellationToken)
{
    for (var row = 0; row < rows; row++)
    {
        for (var column = 0; column < columns; column++)
        {
            cancellationToken.ThrowIfCancellationRequested();

            Process(row, column);
        }
    }
}
```

A check that is not the loop's leading statement (for example, one that appears after other work inside the
loop body) does not satisfy the rule.

- Expression-bodied members (`=>`) are skipped, since they cannot structurally hold a guard statement or a
  cancellation check.
- Members without a body — interface member declarations, `abstract` methods, `extern` methods, and `partial`
  method declarations without an implementation — are skipped, since there is no body to check.
- Both ordinary method declarations and local functions are inspected; lambdas and anonymous methods are not.
- Generated code is skipped.

## How to fix violations

Add a cancellation check as the first statement after any leading guard clauses:

```csharp
// Before
public async Task ProcessAsync(Item item, CancellationToken cancellationToken)
{
    ArgumentNullException.ThrowIfNull(item);

    await SaveAsync(item).ConfigureAwait(false);
}

// After
public async Task ProcessAsync(Item item, CancellationToken cancellationToken)
{
    ArgumentNullException.ThrowIfNull(item);

    cancellationToken.ThrowIfCancellationRequested();

    await SaveAsync(item).ConfigureAwait(false);
}
```

The code fix offers two independent forms — inserting `token.ThrowIfCancellationRequested();`, or inserting
`if (token.IsCancellationRequested) { return ...; }` — for a single occurrence, and via Fix All for every
occurrence in the selected scope. The statement inside the `if` is chosen to match the method or local
function:

- `yield break;`, inside an iterator (one that already uses `yield return`/`yield break`) — `return value;`
  does not compile there at all, regardless of return type.
- A bare `return;`, for a `void`-returning member, or an `async` member returning (non-generic) `Task` or
  `ValueTask`.
- `return [];`, when the effective return type — `T` for an `async` method returning `Task<T>`/`ValueTask<T>`,
  or the declared return type otherwise — is one of the well-known collection shapes (an array, or a generic
  `List<T>`/`ISet<T>`/`ImmutableArray<T>`/`Span<T>`/etc. — see the code fix for the exact set) *and* the
  project's language version supports collection expressions (C# 12+).
- `return default;` otherwise — always syntactically legal, even where it is only a semantic placeholder (for
  example a non-`async` method returning `Task<T>`, where the statement's target type is `Task<T>` itself, not
  `T`, so `Task.FromResult(...)` — not attempted by this mechanical fix — would be needed for a meaningful
  value).

## Suppress a warning

```csharp
#pragma warning disable NE0009
#pragma warning restore NE0009
```
