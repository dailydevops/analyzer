# NE0015: Avoid a redundant Clear() on a freshly created collection

| Property   | Value           |
|------------|-----------------|
| Rule ID    | NE0015          |
| Category   | Maintainability |
| Severity   | Warning         |
| Code fix   | Yes             |

## Cause

A local collection variable is constructed with a parameterless constructor and no collection initializer,
and the first reference to it after that declaration is a parameterless `Clear()` call.

## Rule description

A collection created with `new List<T>()`, `new ArrayList()`, `new Dictionary<TKey, TValue>()`, and similar
is already empty. Calling `Clear()` on it before it has ever been populated has no effect — it is dead code,
typically left over from an edit where the same instance used to be reused across iterations and the
`Clear()` call was never removed once a fresh instance was introduced instead.

```csharp
var list = new List<long>();
list.Clear(); // no-op: list is already empty
```

The rule only reports when it can be certain the call has no effect:

- The receiver must be a **local variable**; fields are out of scope, since their lifetime and aliasing
  cannot be established locally.
- The receiver's type must be **exactly** one of a fixed set of BCL collection types — `List<T>`,
  `ArrayList`, `Dictionary<TKey, TValue>`, `HashSet<T>`, `SortedSet<T>`, `SortedList<TKey, TValue>`,
  `SortedDictionary<TKey, TValue>`, `Queue<T>`, `Stack<T>`, `Collection<T>`, `ObservableCollection<T>` —
  matched by exact type identity, not by interface implementation. A subclass (for example one overriding
  `Collection<T>.ClearItems()` to log or dispose) is deliberately **not** flagged, since its `Clear()` can
  carry arbitrary side effects that this rule has no way to reason about.
- The constructor call must take **no arguments** (a copy-constructor such as `new List<T>(other)`, or a
  capacity constructor such as `new List<T>(16)`, is not flagged) and have **no collection initializer**
  (`new List<T> { 1, 2 }` already populates the instance).
- The `Clear()` call must be the **first reference** to the local after its declaration. Any earlier read or
  write (including passing the local to another method) means the instance may already hold data.
- The `Clear()` call itself must not sit inside a loop that the declaration is not also inside — a
  population loop that runs *after* the call (as in the example below) is fine, since it cannot have
  populated the instance before the call already ran.
- Neither the `Clear()` call nor any other reference to the local may sit inside a lambda, an anonymous
  method, or a local function, and the enclosing block must not contain a `goto` or a label. In any of those
  cases, source order no longer reliably implies execution order, so the rule stays silent rather than risk
  removing a call that does run after the collection has been populated.

## How to fix violations

Remove the redundant call:

```csharp
// Before
var list = new List<long>();
list.Clear();
using (var reader = command.ExecuteReader())
{
    while (reader.Read())
    {
        list.Add((long)reader["Id"]);
    }
}

// After
var list = new List<long>();
using (var reader = command.ExecuteReader())
{
    while (reader.Read())
    {
        list.Add((long)reader["Id"]);
    }
}
```

The code fix removes the `Clear()` statement outright.

## Suppress a warning

```csharp
#pragma warning disable NE0015
#pragma warning restore NE0015
```
